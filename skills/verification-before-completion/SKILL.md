# 完成前验证

## 核心规则

任何完成声明必须有新鲜的验证证据。如果验证命令没有在声明**之前立即运行**，则不能做出声明。

"应该通过"、"可能能用"、"看起来正确"不是验证。只有命令输出确认声明才有效。

## 验证流程

| 步骤 | 操作 | 示例 |
|------|------|------|
| 1. **识别** | 什么命令证明这个声明？ | `pytest tests/`, `npm test` |
| 2. **运行** | **现在运行它** | 不能说"之前运行过" |
| 3. **读取** | 检查完整输出和退出码 | 不要只扫描"passed" |
| 4. **验证** | 输出是否实际确认了声明？ | "42 passed, 0 failed" 确认 |
| 5. **声明** | 只有这时才做出陈述 | 附上可见的证据 |

## 预验证检查

运行验证前检查工作树状态：`git status --porcelain`
- 如果有不相关的未提交更改，先处理
- 验证不能提交在脏树上

## 验证策略（按变更类型）

| 变更类型 | 必需验证 |
|---------|---------|
| 前端（组件、页面、表单） | 启动dev server，测试成功路径和失败路径 |
| 后端处理器/端点 | curl端点，检查响应和错误路径 |
| CLI工具 | 用真实输入运行，检查stdout/stderr/exit code |
| IaC（Terraform、Dockerfile） | `terraform plan` / `docker build` |
| 数据库迁移 | 运行迁移up、down、再up |
| 重构（无行为改变） | 完整测试套件通过 |
| 机械脚本 | 用解析器或编译器验证 |

## 红线

- **清静结果不需要制造发现** — 首次零问题是有效的
- **不要夸大声明** — 命名证明范围
- **测试通过不等于需求满足** — 逐项对照需求检查

## 何时应用

- 声称"测试通过"、"构建成功"、"bug修复"
- 提交、推送、创建PR或标记任务完成
- 向用户报告结果
- 子agent报告委托工作的成功

## 敌对性探测

对于涉及生产逻辑的变更，至少包含一个敌对性探测：

- **边界值**：0, -1, 空字符串, 空数组, null, MAX_INT
- **并发**：两个并行请求使用相同标识符
- **幂等性**：运行相同mutation两次
- **孤儿操作**：删除/更新/获取不存在的ID

## 自我检查

在展示输出前，验证所有成功标准都满足。如有未满足，修订（最多5次迭代）。
